# ADD 完整规范

> 每条规则只出现一次。语言无关，适用于 TypeScript、Python、Rust、Go 等强类型语言。
>
> **定位**：本规范作为项目的一部分存在，是团队开发约定，而非外部调用的工具。

---

## 1. 项目结构

### 1.1 目录组织

**原则：扁平 + 功能聚合**

```
project/
├── .ai-context.md          # 项目级上下文（模块级说明）
├── .ai-context/            # 持久化知识库（可选，大型项目推荐）
│   ├── INDEX.md            # 冷启动入口（< 2000 tokens）
│   ├── systems.md          # 系统边界 + 代码位置
│   ├── dependencies.md     # 依赖关系图
│   └── concept_model.json  # 机器可读知识图谱
├── README.md
├── src/
│   ├── types/              # 全局共享类型
│   ├── modules/            # 业务模块（按功能划分）
│   │   ├── users/
│   │   │   ├── .ai-context.md
│   │   │   ├── types.*
│   │   │   ├── service.*
│   │   │   ├── controller.*
│   │   │   └── test.*
│   │   └── payments/
│   ├── shared/             # 共享工具
│   └── config/
├── tests/                  # 集成/E2E 测试
└── docs/
```

**知识库分层**：

| 层级 | 文件 | 用途 |
|------|------|------|
| 项目级 | `.ai-context.md` | 项目全局上下文，AI 会话入口 |
| 持久化 | `.ai-context/INDEX.md` | 大型项目的冷启动入口（< 2000 tokens） |
| 模块级 | `模块/.ai-context.md` | 单个模块的职责、规则、约束 |

**规则：**

| 项 | 阈值 |
|----|------|
| 目录嵌套 | <= 3 层 |
| 每个目录文件数 | 5-15 个 |
| 功能相关文件 | 放在同一目录（功能聚合，而非按技术类型分散） |

**反模式：** 避免按技术类型分目录（如 `controllers/`、`services/`、`models/` 分散同一功能的文件）。

### 1.2 文件规范

| 项 | 建议值 | 强制上限 |
|----|--------|----------|
| 单文件行数 | < 500 行 | 1000 行（必须拆分） |
| 文件职责 | 一个文件做一件事 | — |

**命名约定：**

| 类型 | 格式 | 示例 |
|------|------|------|
| 文件名 | kebab-case 或 snake_case | `user-service.ts` / `user_service.py` |
| 类/接口 | PascalCase | `UserService` |
| 函数/变量 | camelCase 或 snake_case | 跟随语言惯例 |
| 常量 | UPPER_SNAKE_CASE | `MAX_RETRY_COUNT` |

**文件后缀约定（按职责）：**

```
*.types.*        # 类型定义
*.service.*      # 业务逻辑
*.controller.*   # 外部接口
*.repository.*   # 数据访问
*.test.*         # 测试
.ai-context.md   # AI 上下文说明
```

### 1.3 模块独立性

- 每个模块应自包含：类型 + 逻辑 + 接口 + 测试
- 模块间通过明确定义的接口通信
- 避免循环依赖
- 共享类型放 `src/types/` 或 `src/shared/`
- 用 index 文件暴露模块公共 API，隐藏内部实现

## 2. 代码编写

### 2.1 类型系统（核心护栏）

**优先级：先定义类型，再写实现。**

**规则：**
- 禁止 `any`（或等价的类型逃逸），除非有注释说明原因
- 函数参数和返回值必须显式声明类型
- 用字面量联合类型代替宽泛字符串（如 `'admin' | 'user'` 而非 `string`）
- 用品牌类型 (Branded Type) 防止 ID 混淆（如 `UserId` vs `OrderId`）

### 2.2 函数设计

| 项 | 建议值 | 警告值 |
|----|--------|--------|
| 函数行数 | < 50 行 | > 80 行 |
| 参数数量 | <= 4 个 | > 6 个（改用对象参数） |
| 嵌套层级 | <= 3 层 | > 5 层（提前 return） |

**实践：**
- 单一职责：每个函数只做一件事
- 命名自解释：`createUser(input)` 而非 `process(data)`
- 提前返回减少嵌套，而非多层 if-else

**命名动词约定：**

| 语义 | 推荐动词 |
|------|---------|
| 获取 | `get`, `find`, `fetch`, `query` |
| 创建 | `create`, `add`, `insert` |
| 更新 | `update`, `patch`, `modify` |
| 删除 | `delete`, `remove` |
| 验证 | `validate`, `check`, `verify` |
| 转换 | `normalize`, `format`, `transform` |

### 2.3 编码风格

- 项目内代码风格必须一致（配置格式化工具自动执行）
- 常量提取：禁止魔术数字/字符串
- 保持一致的错误处理模式

## 3. 文档

### 3.1 文档层级

```
项目级     README.md + .ai-context.md    → 项目全局上下文
模块级     每个核心模块/.ai-context.md    → 模块职责、规则、约束
代码级     函数注释（JSDoc/docstring）    → 公共 API 的 What + Why
行内       行内注释                       → 解释非显而易见的 Why
```

### 3.2 注释原则

**解释 Why，不是 What。** AI 能看懂代码做了什么，但需要知道为什么这么做。

```
// BAD: 增加计数器
count++;

// GOOD: 重试次数 +1，用于指数退避算法
retryCount++;
```

**TODO 格式：** `// TODO(scope): 描述 - 日期`

### 3.3 公共 API 文档

公共函数/方法必须包含：
- 功能描述
- 参数说明
- 返回值说明
- 可能抛出的异常
- 使用示例（复杂 API）

私有辅助函数：名字自解释即可，无需文档注释。

### 3.4 README 必备章节

1. 一句话描述 + 快速启动（3 步以内）
2. 项目目标 + 技术栈
3. **AI 开发指南**（专门写给 AI Agent 的操作规则）
4. 目录结构
5. 开发命令

## 4. 审查清单

### 快速检查（5 分钟）

```
□ 文件 < 1000 行
□ 函数 < 80 行
□ 无 any / 类型逃逸
□ 测试通过
□ 文档已同步更新
```

### 详细审查（15 分钟）

**代码质量：**
- [ ] 类型定义完整，无隐式类型
- [ ] 命名自解释，无模糊命名
- [ ] 无魔术数字
- [ ] 无超过 5 层嵌套
- [ ] 代码风格与项目一致

**文档完整性：**
- [ ] 核心模块有 `.ai-context.md`
- [ ] 公共 API 有文档注释
- [ ] 注释解释 Why 而非 What

**测试覆盖：**
- [ ] 新功能有对应测试
- [ ] 核心业务逻辑覆盖率 > 80%
- [ ] 包含边界情况和错误处理测试

**架构与安全（人类审查重点）：**
- [ ] 业务意图是否正确（AI 无法判断）
- [ ] 模块职责是否清晰，无循环依赖
- [ ] 无安全隐患（输入验证、权限检查、敏感信息泄露）
- [ ] 性能无明显隐患

### 审查流程

```
小改动：  AI 生成 → AI 自查 → 人类快速审查 → 合并
大改动：  AI 生成 → AI 自查 → AI 报告待审点 → 人类详细审查 → AI 修改 → 合并
```

## 5. 知识库管理

### 5.1 持久化知识库结构

大型项目推荐创建 `.ai-context/` 目录，作为 AI 会话间的"记忆传递"：

```
.ai-context/
├── INDEX.md            # 冷启动入口（< 2000 tokens）
├── systems.md          # 系统边界 + 代码位置
├── dependencies.md     # 依赖关系图（可用 Mermaid）
├── test_coverage.md    # 静态测试面
└── concept_model.json  # 机器可读知识图谱
```

### 5.2 INDEX.md 规范

**硬约束**：
- 全文 **< 2000 tokens**（约 60-70 行中文，100-120 行英文）
- 包含项目核心架构、关键入口、重要约定
- 结论必须具体，证据不足时明确写出 `evidence gap`

**推荐结构**：

```markdown
# 项目名称 - AI 快速上下文

> generated_by: 团队维护
> verified_at: 2026-03-10
> provenance: 人工编写 + 代码验证

## 核心架构
- 入口：`src/index.ts`
- 主要模块：users / orders / payments

## 关键约定
- API 响应格式：`{ code, data, message }`
- 错误处理：统一抛出 `AppError`

## 证据缺口
- payments 模块的异步流程尚未在代码中实现
```

### 5.3 Provenance 标注规范

所有知识库文件必须包含头部标注：

```markdown
> generated_by: <来源>
> verified_at: <日期>
> provenance: <信息来源说明>
```

**provenance 值示例**：

| 值 | 含义 |
|---|------|
| `code-verified` | 代码中已验证 |
| `docs-inferred` | 从文档推断 |
| `manual-review` | 人工审查确认 |
| `partial-coverage` | 部分覆盖（需说明缺口） |

### 5.4 信息状态标记

在描述系统组件时，明确标记状态：

| 状态 | 含义 | 示例 |
|------|------|------|
| `implemented` | 已实现，有代码 | `code_path: src/users/` |
| `planned` | 计划中，有设计文档 | `evidence_path: docs/design.md` |
| `inferred` | 推断得出，需验证 | `evidence_gap: 缺少直接证据` |

**禁止行为**：
- `implemented` 状态但 `code_path` 不存在
- `planned/inferred` 状态伪造精确路径
- 用模糊词替代证据缺口说明

## 6. 不确定性表达规范

### 6.1 禁止裸写模糊词

```
❌ 禁止单独使用：
待确认 · 可能是 · 疑似 · 也许 · 待定 · 暂不清楚 · 需要进一步 · 不确定
pending · maybe · possibly · perhaps · TBD
```

### 6.2 正确表达方式

**可以保留不确定，但必须指出缺失的是哪一类证据**：

```markdown
✅ 推荐：
evidence gap: 未发现 `src/server/` 被任何入口文件直接引用，因此暂不把它标记为主系统。
unknown: 项目缺少 git 历史，无法判断真实热点文件。
partial: payments 模块仅有接口定义，实现代码尚未合并。
```

### 6.3 结论优先级

在文档中，**优先写已验证事实，再写尚未验证部分**：

```markdown
## 用户模块

✅ 已验证：
- 入口：`src/users/controller.ts`
- 数据模型：`src/users/types.ts`

⚠️ 待验证：
- 缓存策略：设计文档提到 Redis，但代码中未发现实现
```

## 7. 开发流程中的质疑机制

借鉴 PROBE 协议思想，防止"第一眼假设变结论"。

### 7.1 AI 生成代码前的自检

AI 在生成重要代码前，应自问：

1. **这个模块的真实入口在哪里？**（不要只凭目录名猜测）
2. **改这个接口会影响哪些地方？**（用依赖分析验证）
3. **有没有相反的证据？**（查看 git 热点、测试覆盖）

### 7.2 人类审查时的质疑点

当 AI 提交代码时，人类应质疑：

| 质疑类型 | 示例问题 |
|----------|----------|
| 结构质疑 | "为什么 `core/` 没有任何文件被外部引用？" |
| 依赖质疑 | "这个模块说自己是入口，但 `main.py` 没有导入它？" |
| 一致性质疑 | "git 显示 `utils.ts` 改动最多，但它被标记为'稳定'？" |

### 7.3 质疑格式

```markdown
Q: [具体的矛盾或可疑之处]
证据线索: [文件路径/行号/git 数据]
验证计划: [如何验证]
```

**合格示例**：

```markdown
Q: git 显示 `tasks/analysis.py` 变更 21 次（high risk），
   但 AI 认为入口是 `main.py`。为何 `analysis.py` 热度更高？
证据线索: git log 显示 `tasks/analysis.py` 最近 30 天 21 次提交
验证计划: 查看 `analysis.py` 的 import 关系，确认是否是真实入口
```

**不合格示例**（禁止提交）：

```markdown
Q: 我对系统结构的把握还不够扎实
Q: xxx 目录的职责暂时没有直接证据
```

## 8. 持久化开发规则

将以下规则写入项目的 `AGENTS.md` 或 `.ai-context.md`，让 AI 在每次会话自动遵循：

```markdown
## AI 会话规则

1. 如果 `.ai-context/INDEX.md` 存在，开始任务前必须先阅读它恢复全局上下文。

2. 重要修改前，先验证依赖关系：
   - 检查目标文件的上游依赖和下游被依赖者
   - 评估改动影响半径

3. 当任务改变了项目的结构认知时，评估是否需要更新 `.ai-context/`：
   - 新增核心模块
   - 修改关键入口
   - 变更重要约定

4. 诚实地表达不确定性：
   - 证据不足时明确写出 `evidence gap`
   - 不用模糊词掩盖知识缺口
```
